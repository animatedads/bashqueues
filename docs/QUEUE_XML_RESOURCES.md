# Queue XML resources

XML resources are non-executable presentation resources for tools that need a stable human-facing XML layout, such as panels, export adapters, or documentation generators. They are deliberately not a job-control format and not a provider contract.

## Purpose

Use XML resources only for display and layout templates. Structured machine contracts remain JSON and are generated by command code, not by localized or display templates.

Good uses:

- human-facing panel fragments
- rendered job cards
- printable status summaries
- localized labels around already-structured values

Do not use XML resources for:

- queue dispatch decisions
- provider authority
- policy decisions
- secrets delivery
- command JSON output
- shell scripts or executable snippets

## Layout

XML resources live beside display resources:

```text
resources.d/xml/lang_eng/job-card.example.xml
resources.d/xml/fallback/job-card.example.xml
```

The language directory follows the same resource naming convention used by display resources. The fallback directory is the emergency non-localized display fallback.

## Token replacement

Only controlled double-brace tokens are allowed:

```text
{{QID}}
{{JOB_NAME}}
{{STATE}}
{{CLASS}}
{{UPDATED_AT}}
```

The renderer must treat resource content as data. It must not use `eval`, `source`, command substitution, shell expansion, or XML external entities.

Forbidden resource constructs include shell expansion and executable-looking payloads:

```text
${TOKEN}
$(command)
`command`
<!ENTITY external SYSTEM "file:///etc/passwd">
```

## XML safety rules

XML resources must be parseable XML fragments or documents. The first package keeps this contract static and fixture-first:

- no DTD
- no external entity declarations
- no processing instructions that invoke local tools
- no secrets or secret placeholders
- no provider credentials
- no command lines containing secret values
- no JSON contract generation from XML display templates

## Secrets boundary

Display and XML resources must never render secret values. Secret-aware commands may render redacted labels such as `redacted=true`, `delivery=file`, or a non-sensitive audit identifier, but the secret value must stay out of templates, logs, scratchpad entries, examples, and patchsets.

This keeps Bob18's display-resource lane separate from Bob17's governed secrets broker lane.

## Example

```xml
<queue-job-card schema="queuebash.display.xml.job_card.v1">
  <qid>{{QID}}</qid>
  <name>{{JOB_NAME}}</name>
  <state>{{STATE}}</state>
  <class>{{CLASS}}</class>
  <updated-at>{{UPDATED_AT}}</updated-at>
</queue-job-card>
```

## Validation expectations

Static validation should confirm that XML resources are present, parseable, non-executable, free of shell expansion, free of DTD/external-entity declarations, and separate from JSON command contracts.
